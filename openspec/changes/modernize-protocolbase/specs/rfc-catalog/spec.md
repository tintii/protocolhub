## ADDED Requirements

### Requirement: Official RFC metadata snapshot
The RFC catalog SHALL use a committed, validated snapshot of the official RFC Editor index containing all published RFC entries available at capture time. It SHALL record the source URL, retrieval timestamp, and checksum. Each entry SHALL include its number, title, and official document URL and preserve available authors, publication date, abstract, status, series, and update/obsolescence relationships.

#### Scenario: Browse an RFC record
- **WHEN** a reader opens an RFC entry
- **THEN** its identifying metadata, available relationships, and official document link are displayed
- **AND** the catalog makes the snapshot date visible without presenting its status metadata as live

### Requirement: Local discovery and authoritative reading
The RFC page SHALL provide search over number, title, authors, and available abstracts; numeric lookup; static browsing in ascending and descending number order; and pagination. It SHALL provide links to authoritative HTTPS documents and the live RFC Editor search. The site SHALL NOT mirror RFC bodies or imply its local search covers full RFC document text.

#### Scenario: Find by title or author
- **WHEN** a reader searches an RFC title phrase or author name present in the snapshot
- **THEN** matching RFC records are displayed with their number, title, and destination

#### Scenario: Browse with JavaScript disabled
- **WHEN** a reader disables JavaScript and navigates RFC browse pages
- **THEN** all snapshot entries remain reachable through static pagination and official document links

### Requirement: Stable search destinations and protocol connections
RFC browse pages and search records SHALL derive entry URLs from the same build manifest. RFC entries SHALL link back to protocol records that cite them, and protocol citations SHALL resolve to the corresponding catalog entry or official document. Malformed historical references SHALL be retained as explicit unresolved-source information without inventing an RFC identifier.

#### Scenario: Follow an RFC search result
- **WHEN** a reader follows an RFC result generated by the current build
- **THEN** it opens the static browse page containing that RFC and targets its entry anchor
- **AND** any protocols citing it are linked from the entry

#### Scenario: New protocol references an absent RFC
- **WHEN** a new record references a valid-format RFC number absent from the snapshot and validated supplemental metadata
- **THEN** validation identifies the missing RFC and instructs the contributor to refresh or add sourced metadata

### Requirement: Explicit and failure-safe refresh
An explicit maintenance command SHALL retrieve and validate the official index before replacing the committed snapshot. Validation SHALL reject duplicate numbers, missing required fields, malformed data, and external XML entity expansion. Refresh failure SHALL leave the previous snapshot intact. Ordinary site builds SHALL consume committed metadata without fetching upstream content.

#### Scenario: Upstream refresh fails
- **WHEN** the upstream request fails or returns invalid metadata
- **THEN** the refresh command reports failure and retains the previous valid snapshot unchanged
- **AND** normal builds continue to use that snapshot

#### Scenario: Successful refresh
- **WHEN** a valid updated index is retrieved
- **THEN** the command produces a reviewable metadata diff and updated provenance
- **AND** the next build regenerates RFC browse pages, protocol backlinks, and search destinations consistently
