<section aria-labelledby="description">
<h2 id="description">Description</h2>

			The Simple Network Management Protocol (SNMP) is an application layer protocol that facilitates the exchange of management information between network devices. SNMP enables network administrators to manage network performance, find and solve network problems, and plan for network growth.
<br />
<br />SNMP is essentially a request-reply protocol running over UDP, though TCP operation is possible. SNMP is an asymmetric protocol, operating between a management station (smart) and an agent (dumb). 
<br /><hr />
<br /><b>SNMP Basic Components</b>
<br />An SNMP-managed network consists of three key components: managed devices, agents, and network-management systems (NMSs).
<br />
<br />A managed device is a network node that contains an SNMP agent and that resides on a managed network. Managed devices collect and store management information and make this information available to NMSs using SNMP. Managed devices, sometimes called network elements, can be routers and access servers, switches and bridges, hubs, computer hosts, or printers.
<br />
<br />An agent is a network-management software module that resides in a managed device. An agent has local knowledge of management information and translates that information into a form compatible with SNMP.
<br />
<br />An NMS executes applications that monitor and control managed devices. NMSs provide the bulk of the processing and memory resources required for network management. One or more NMSs must exist on any managed network.
<br />
<br />Two versions of SNMP exist: SNMP version 1 (SNMPv1) and SNMP version 2 (SNMPv2). Both versions have a number of features in common, but SNMPv2 offers enhancements, such as additional protocol operations. Standardization of yet another version of SNMP¡ªSNMP Version 3 (SNMPv3)¡ªis pending. This chapter provides descriptions of the SNMPv1 and SNMPv2 protocol operations. Figure 56-1 illustrates a basic network managed by SNMP.
<br />
<br /><b>SNMP Management</b>
<br />SNMP is a distributed-management protocol. A system can operate exclusively as either an NMS or an agent, or it can perform the functions of both. When a system operates as both an NMS and an agent, another NMS might require that the system query manage devices and provide a summary of the information learned, or that it report locally stored management information.
<br /><hr />
<br /><b>SNMP Message Format</b>
<br />SNMP is a session protocol which is encapsulated in UDP. The SNMP message format is shown below:
<br /><div><div class="table-scroll" role="region" aria-label="Description table 1" tabindex="0"><table><caption>Description: preserved table 1</caption><tbody><tr><td><p>Version </p></td><td><p>Community </p></td><td><p>PDU </p></td></tr></tbody></table></div></div>
<br /><ul><li><b>Version</b><br /></li>
<li>SNMP version number. Both the manager and agent must use the same version of SNMP. Messages containing different version numbers are discarded without further processing.
<br /><br /></li>
<li><b>Community</b><br /></li>
<li>Community name used for authenticating the manager before allowing access to the agent.
<br /><br /></li>
<li><b>PDU</b><br /></li>
<li><ul><li><b>PDU Format</b><br /></li>
<li>GetRequest, GetNext Request, GetResponse and SetRequest PDUs format.
<br /></li><li><div><div class="table-scroll" role="region" aria-label="Description table 2" tabindex="0"><table><caption>Description: preserved table 2</caption><tbody><tr><td><p>PDU type</p></td><td><p>Request ID</p></td><td><p>Error status</p></td><td><p>Error index</p></td><td><p>Object 1, value 1</p></td><td><p>Object 2, value 2</p></td></tr></tbody></table></div></div><br /></li>
<li><ul><li><b>PDU type</b><br /></li>
<li>Specifies the type of PDU:
<br /></li><li><div><div class="table-scroll" role="region" aria-label="Description table 3" tabindex="0"><table><caption>Description: preserved table 3</caption><tbody><tr><td><p>0</p></td><td><p>GetRequest.</p></td></tr><tr><td><p>1</p></td><td><p>GetNextRequest.</p></td></tr><tr><td><p>2</p></td><td><p>GetResponse.</p></td></tr><tr><td><p>3</p></td><td><p>SetRequest.</p></td></tr></tbody></table></div></div><br /></li>
<li><ul><li><b>GetRequest</b><br /></li>
<li>The GetRequest-PDU is generated by a protocol entity only at the request of its SNMP application entity. 
<br /><br /></li>
<li><b>GetNextRequest</b><br /></li>
<li>The form of the GetNextRequest-PDU is identical to that of the GetRequest-PDU except for the indication of the PDU type.  The GetNextRequest-PDU is generated by a protocol entity only at the request of its SNMP application entity.
<br /><br /></li>
<li><b>GetResponse</b><br /></li>
<li>The form of the GetResponse-PDU is identical to that of the GetRequest-PDU except for the indication of the PDU type. The GetResponse-PDU is generated by a protocol entity only upon receipt of the GetRequest-PDU, GetNextRequest-PDU, or SetRequest-PDU, as described elsewhere in this document.
<br /><br /></li>
<li>Upon receipt of the GetResponse-PDU, the receiving protocol entity presents its contents to its SNMP application entity.
<br /><br /></li>
<li><b>SetRequest</b><br /></li>
<li>The form of the SetRequest-PDU is identical to that of the GetRequest-PDU except for the indication of the PDU type. The SetRequest-PDU is generated by a protocol entity only at the request of its SNMP application entity.
<br /><br /></li>
<li><b>Trap</b><br /></li>
<li>The Trap-PDU is generated by a protocol entity only at the request of the SNMP application entity.  The means by which an SNMP application entity selects the destination addresses of the SNMP application entities is implementation-specific.</li></ul><br /></li>
<li><b>Request ID</b><br /></li>
<li>Integer field which correlates the manager¡¯s request to the agent¡¯s response.
<br /><br /></li>
<li><b>Error status</b><br /></li>
<li>Enumerated integer type that indicates normal operation or one of five error conditions. The possible values are:
<br /></li><li><div><div class="table-scroll" role="region" aria-label="Description table 4" tabindex="0"><table><caption>Description: preserved table 4</caption><tbody><tr><td><p>0</p></td><td><p>noError: Proper manager/agent operation.</p></td></tr><tr><td><p>1</p></td><td><p>tooBig: Size of the required GetResponse PDU exceeds a local limitation.</p></td></tr><tr><td><p>2</p></td><td><p>noSuchName: The requested object name does not match the names available in the relevant MIB View.</p></td></tr><tr><td><p>3</p></td><td><p>badValue: A SetRequest contains an inconsistent type, length and value for the variable.</p></td></tr><tr><td><p>4</p></td><td><p>readOnly.</p></td></tr><tr><td><p>5</p></td><td><p>genErr: Other errors, which are not explicitly defined, have occurred.</p></td></tr></tbody></table></div></div><br /></li>
<li><b>Error index</b><br /></li>
<li>Identifies the entry within the variable bindings list that caused the error.
<br /><br /></li>
<li><b>Object/value</b><br /></li>
<li>Variable binding pair of a variable name with its value.</li></ul><br /></li>
<li><b>Trap PDU Format</b><br /></li>
<li><div><div class="table-scroll" role="region" aria-label="Description table 5" tabindex="0"><table><caption>Description: preserved table 5</caption><tbody><tr><td><p>PDU type</p></td><td><p>Enterprise</p></td><td><p>Agent address</p></td><td><p>Gen trap type</p></td><td><p>Spec trap type</p></td><td><p>Time stamp</p></td><td><p>Object/value</p></td></tr></tbody></table></div></div><br /></li>
<li><ul><li><b>PDU type</b><br /></li>
<li>Specifies the type of PDU (4=Trap).
<br /><br /></li>
<li><b>Enterprise</b><br /></li>
<li>Identifies the management enterprise under whose registration authority the trap was defined.
<br /><br /></li>
<li><b>Agent address</b><br /></li>
<li>IP address of the agent, used for further identification.
<br /><br /></li>
<li><b>Generic trap type</b><br /></li>
<li>Field describing the event being reported. The following seven values are defined:
<br /></li><li><div><div class="table-scroll" role="region" aria-label="Description table 6" tabindex="0"><table><caption>Description: preserved table 6</caption><tbody><tr><td>0</td><td>coldStart: Sending protocol entity has reinitialized, indicating that the agent"s configuration or entity implementation may be altered.</td></tr><tr><td>1</td><td>warmStart: Sending protocol has reinitialized, but neither the agent"s configuration nor the protocol entity implementation has been altered.</td></tr><tr><td>2</td><td>linkDown: A communication link has failed.</td></tr><tr><td>3</td><td>linkUp: A communication link has come up.</td></tr><tr><td>4</td><td>authenticationFailure: The agent has received an improperly authenticated SNMP message from the manager, i.e., community name was incorrect.</td></tr><tr><td>5</td><td>egpNeighborLoss: An EGP peer neighbor is down.</td></tr><tr><td>6</td><td>enterpriseSpecific: A non-generic trap has occurred which is further identified by the Specific Trap Type and Enterprise fields.</td></tr></tbody></table></div></div><br /></li>
<li><b>Specific trap type</b><br /></li>
<li>Used to identify a non-generic trap when the Generic Trap Type is enterpriseSpecific.
<br /><br /></li>
<li><b>Timestamp</b><br /></li>
<li>Value of the sysUpTime object, representing the amount of time elapsed between the last (re-)initialization and the generation of that Trap.
<br /><br /></li>
<li><b>Object/value</b><br /></li>
<li>Variable binding pair of a variable name with its value.</li></ul></li></ul></li></ul>
<br /><hr />
<br /><b>SNMP Architecture</b>
<br />Implicit in the SNMP architectural model is a collection of network management stations and network elements. Network management stations execute management applications which monitor and control network elements. Network elements are devices such as hosts, gateways, terminal servers, and the like, which have management agents responsible for performing the network management functions requested by the network management stations. The Simple Network Management Protocol (SNMP) is used to communicate management information between the network management stations and the agents in the network elements.
<br />
<br /><ul><li><b>Goals of the Architecture</b><br /></li>
<li>The SNMP explicitly minimizes the number and complexity of management functions realized by the management agent itself. This goal is attractive in at least four respects:
<br /></li><li><ul><li>The development cost for management agent software necessary to support the protocol is accordingly reduced.<br /><br /></li>

<li>The degree of management function that is remotely supported is accordingly increased, thereby admitting fullest use of internet resources in the management task.<br /><br /></li>

<li>The degree of management function that is remotely supported is accordingly increased, thereby imposing the fewest possible restrictions on the form and sophistication of management tools.<br /><br /></li>

<li>Simplified sets of management functions are easily understood and used by developers of network management tools.</li></ul><br /></li>
<li>A second goal of the protocol is that the functional paradigm for monitoring and control be sufficiently extensible to accommodate additional, possibly unanticipated aspects of network operation and management.
<br /><br /></li>
<li>A third goal is that the architecture be, as much as possible, independent of the architecture and mechanisms of particular hosts or particular gateways.
<br /><br /></li>
<li><b>Elements of the Architecture</b><br /></li>
<li>The SNMP architecture articulates a solution to the network management problem in terms of:
<br /></li><li><ul><li><b>The scope of the management information</b><br /></li>
<li>The scope of the management information communicated by operation of the SNMP is exactly that represented by instances of all non-aggregate object types either defined in Internet-standard MIB or defined elsewhere according to the conventions set forth in Internet-standard SMI.
<br /><br /></li>
<li><b>The representation of the management information</b><br /></li>
<li>Management information communicated by operation of the SNMP is represented according to the subset of the ASN.1 language that is specified for the definition of non-aggregate types in the SMI.
<br /><br /></li>
<li><b>Operations on management information</b><br /></li>
<li>The SNMP models all management agent functions as alterations or inspections of variables. Thus, a protocol entity on a logically remote host (possibly the network element itself) interacts with the management agent resident on the network element in order to retrieve (get) or alter (set) variables. This strategy has at least two positive consequences:
<br /></li><li><ul><li>It has the effect of limiting the number of essential management functions realized by the management agent to two: one operation to assign a value to a specified configuration or other parameter and another to retrieve such a value.
<br /><br /></li>
<li>A second effect of this decision is to avoid introducing into the protocol definition support for imperative management commands:  the number of such commands is in practice ever-increasing, and the semantics of such commands are in general arbitrarily complex.</li></ul><br /></li>
<li><b>Form and Meaning of Protocol Exchanges</b><br /></li>
<li>The communication of management information among management entities is realized in the SNMP through the exchange of protocol messages.
<br /><br /></li>
<li><b>Definition of Administrative Relationships</b><br /></li>
<li>The SNMP architecture admits a variety of administrative relationships among entities that participate in the protocol. The entities residing at management stations and network elements which communicate with one another using the SNMP are termed SNMP application entities.  The peer processes which implement the SNMP, and thus support the SNMP application entities, are termed protocol entities.
<br /><br /></li>
<li><b>Form and Meaning of References to Managed Objects.</b><br /></li>
<li>The SMI requires that the definition of a conformant management protocol address:
<br /></li><li><ul><li>Resolution of ambiguous MIB references.<br /></li>
<li>Because the scope of any SNMP operation is conceptually confined to objects relevant to a single network element, and because all SNMP references to MIB objects are (implicitly or explicitly) by unique variable names, there is no possibility that any SNMP reference to any object type defined in the MIB could resolve to multiple instances of that type.
<br /><br /></li>
<li>Resolution of References across MIB Versions.<br /></li>
<li>The object instance referred to by any SNMP operation is exactly that specified as part of the operation request or (in the case of a get-next operation) its immediate successor in the MIB as a whole.
<br /><br /></li>
<li>Identification of Object Instances.<br /></li>
<li>The names for all object types in the MIB are defined explicitly either in the Internet-standard MIB or in other documents which conform to the naming conventions of the SMI.  The SMI requires that conformant management protocols define mechanisms for identifying individual instances of those object types for a particular network element.
<br /><br /></li>
<li>The type-specific naming of object instances is defined below for a number of classes of object types.  Instances of an object type to which none of the following naming conventions are applicable are named by OBJECT IDENTIFIERs of the form x.0, where x is the name of said object type in the MIB definition.
<br /><br /></li>
<li>For example, suppose one wanted to identify an instance of the variable sysDescr The object class for sysDescr is:
<br /></li><li>          iso org dod internet mgmt mib system sysDescr
<br /></li><li>           1   3   6     1      2    1    1       1
<br /><br /></li>
<li>Hence, the object type, x, would be 1.3.6.1.2.1.1.1 to which is appended an instance sub-identifier of 0.  That is, 1.3.6.1.2.1.1.1.0 identifies the one and only instance of sysDescr.</li></ul></li></ul></li></ul>

<section aria-labelledby="examples">
<h2 id="examples">Examples</h2>

			<pre class="legacy-pre" role="region" aria-label="Examples: preformatted example 1" tabindex="0"><b>Example 1: Table Traversal</b>

By the SNMP exchange sketched below, an SNMP application entity might extract the 
destination address and next hop gateway for each entry in the routing table of a 
particular network element. Suppose that this routing table has three entries:

          Destination           NextHop            Metric
          10.0.0.99             89.1.1.42          5
          9.1.2.3               99.0.0.3           3
          10.0.0.51             89.1.1.42          5

The management station sends to the SNMP agent a GetNextRequest-PDU containing 
the indicated OBJECT IDENTIFIER values as the requested variable names:

GetNextRequest ( ipRouteDest, ipRouteNextHop, ipRouteMetric1 )

The SNMP agent responds with a GetResponse-PDU:

              GetResponse (( ipRouteDest.9.1.2.3 =  "9.1.2.3" ),
                      ( ipRouteNextHop.9.1.2.3 = "99.0.0.3" ),
                      ( ipRouteMetric1.9.1.2.3 = 3 ))

The management station continues with:

              GetNextRequest ( ipRouteDest.9.1.2.3,
                      ipRouteNextHop.9.1.2.3,

                      ipRouteMetric1.9.1.2.3 )

The SNMP agent responds:

              GetResponse (( ipRouteDest.10.0.0.51 = "10.0.0.51" ),
                      ( ipRouteNextHop.10.0.0.51 = "89.1.1.42" ),
                      ( ipRouteMetric1.10.0.0.51 = 5 ))

The management station continues with:

              GetNextRequest ( ipRouteDest.10.0.0.51,
                      ipRouteNextHop.10.0.0.51,
                      ipRouteMetric1.10.0.0.51 )

The SNMP agent responds:

              GetResponse (( ipRouteDest.10.0.0.99 = "10.0.0.99" ),
                      ( ipRouteNextHop.10.0.0.99 = "89.1.1.42" ),
                      ( ipRouteMetric1.10.0.0.99 = 5 ))

The management station continues with:

              GetNextRequest ( ipRouteDest.10.0.0.99,

<section aria-labelledby="glossary">
<h2 id="glossary">Local glossary</h2>

			<div>
			<b>MIB</b><br />MIB (Management Information Base) is database of objects that can be monitored by a network management system. Both SNMP and RMON use standardized MIB formats that allows any SNMP and RMON tools to monitor any device defined by a MIB.<br /><br /><b>NMSs</b><br />NMSs (network-management systems) is an NMS executes applications that monitor and control managed devices.
<br /><br /><br /><b>SMI</b><br />SMI(Structure of Management Information) is a component of network management systems that defines the structure of management information as a tree with objects as leaves.<br /><br /><b>SNMP Architecture</b><br />SNMP architectural model is a collection of network management stations and network elements.
